# CTI V1.1–V1.3 统一产品设计原则与 AI 开发约束

## 一、产品总体目标

Crypto Trend Intelligence（CTI）不是简单的行情展示系统，也不是单纯的技术指标打分工具。

产品最终目标是构建一套完整的加密资产投资研究与决策辅助系统：

1. 识别市场环境和市场趋势。
2. 解释市场变化的原因，形成可追溯的市场情报。
3. 评估不同加密资产的投资价值和风险。
4. 根据账户资金、持仓和风险偏好生成投资决策建议。
5. 根据市场环境选择适合的投资策略。
6. 持续验证策略的有效性，识别策略失效和市场环境变化。

系统必须遵循：

**先判断市场，再评估资产，然后管理资金，最后选择和验证策略。**

V1.1、V1.2、V1.3 必须构建在 V1.0 已有的数据采集、指标计算、评分、信号和回测能力之上，不允许重复建设基础能力。

## 二、三个版本的额外产品建议

### V1.1：市场情报与趋势解释

产品目标：从“告诉用户一个币得了多少分”，升级为“告诉用户市场发生了什么、为什么发生、哪些信息支持这个判断”。

必须考虑以下设计：

1. 市场整体环境分析：
    - BTC 趋势及关键支撑阻力区域。
    - ETH 相对 BTC 的强弱变化。
    - 主流山寨币整体表现。
    - 市场上涨、下跌、横盘的广度。
    - 市场波动率变化。
    - 市场风险状态。

2. 币种个体分析：
    - 当前趋势方向。
    - 中短期动量。
    - 相对 BTC 的强弱。
    - 成交量是否确认价格变化。
    - 是否发生趋势突破、趋势衰减或反转。
    - 当前价格距离关键趋势指标的位置。

3. 市场异动发现：
    - 价格异常波动。
    - 成交量异常放大。
    - 突破近期高低点。
    - 相对 BTC 强弱突然变化。
    - 市场广度快速恶化。
    - 波动率突然上升。

4. 形成结构化市场情报：
    - 事件发生时间。
    - 影响币种。
    - 事件类型。
    - 观测数据。
    - 影响方向。
    - 影响程度。
    - 数据来源。
    - 可信度。
    - 是否已经被后续行情验证。

5. 新闻和情绪信息：
    - 作为辅助信息，不允许直接替代价格和成交量趋势判断。
    - 必须区分事实、市场观点和模型推测。
    - 新闻来源、发布时间和采集时间必须保存。
    - 不允许仅凭新闻标题直接生成 BUY 信号。
    - 对无法验证的信息降低可信度。

额外建议：

- 建立市场日报和市场异动报告。
- 每次生成市场判断时保存当时的数据快照和模型版本。
- 支持查看历史某一天系统为什么看多或看空。
- 对每个判断提供支持证据和反向证据。
- 不允许只输出结论，不输出理由。
- 不允许将相关性描述成因果关系。

### V1.2：投资决策与组合风险管理

产品目标：从单币信号升级为账户级投资决策系统。

必须考虑以下设计：

1. 账户资金管理：
    - 总资产。
    - 可用现金。
    - 已投资金额。
    - 未实现盈亏。
    - 已实现盈亏。
    - 各币种持仓占比。
    - 资产集中度。

2. 投资组合管理：
    - BTC、ETH、山寨币之间的资金分配。
    - 单币最大持仓比例。
    - 山寨币总仓位限制。
    - 现金储备比例。
    - 资产相关性和集中度。
    - 组合整体波动率和最大回撤。

3. 交易决策：
    - 新买入建议。
    - 加仓建议。
    - 减仓建议。
    - 止盈建议。
    - 止损建议。
    - 退出建议。
    - 暂不操作建议。

4. 仓位计算：
    - 根据账户净值计算风险预算。
    - 根据 ATR 和止损距离计算合理仓位。
    - 根据单币上限、组合上限和现金余额进行约束。
    - 考虑交易手续费和滑点。
    - 避免仅凭评分高低决定投入金额。

5. 风险管理：
    - 单笔交易风险。
    - 单币集中度风险。
    - 组合回撤风险。
    - BTC 系统性风险。
    - 高相关资产同时下跌的风险。
    - 流动性不足风险。
    - 连续亏损后的风险收缩机制。

额外建议：

- 必须区分“信号”和“投资决策”。信号是市场判断，投资决策还必须考虑账户持仓和资金约束。
- 同一个 BUY 信号，在不同账户中可能产生不同的投资建议。
- 必须支持模拟账户和模拟交易。
- 必须记录每次决策的输入、输出、原因和策略版本。
- 必须支持投资组合历史净值曲线。
- 必须支持与 BTC Buy & Hold、简单持仓策略进行比较。
- V1.2 不得默认执行真实交易，不得要求用户提供交易权限。
- 当市场风险过高时，允许系统给出保持现金、不操作的建议。

### V1.3：策略研究与智能分析

产品目标：从固定规则的趋势评分系统升级为能够研究、评估和选择策略的研究平台。

必须考虑以下设计：

1. 市场环境分类：
    - 牛市趋势。
    - 熊市趋势。
    - 震荡市场。
    - 高波动市场。
    - 低波动市场。
    - 市场状态转换。

2. 策略库：
    - 均线趋势策略。
    - Donchian 突破策略。
    - 动量策略。
    - 相对强弱策略。
    - 趋势回撤入场策略。
    - 多策略组合策略。

3. 策略评估：
    - CAGR。
    - Sharpe。
    - Sortino。
    - 最大回撤。
    - Calmar。
    - 胜率。
    - Profit Factor。
    - 换手率。
    - 手续费占比。
    - 不同市场环境下的收益表现。

4. 策略选择：
    - 根据当前市场环境评估策略适用性。
    - 比较多个候选策略的历史表现。
    - 识别策略在当前环境中的潜在风险。
    - 输出推荐策略及其选择依据。
    - 不允许仅根据历史收益最高选择策略。

5. 策略失效监控：
    - 近期表现明显偏离历史统计。
    - 回撤超过预设阈值。
    - 连续亏损异常。
    - 策略信号频率异常。
    - 策略收益风险比恶化。
    - 市场环境发生变化。

6. 策略优化：
    - 参数敏感性分析。
    - Walk-forward 验证。
    - Out-of-sample 验证。
    - 不同币种和不同时间段的稳定性测试。
    - 交易成本变化压力测试。

额外建议：

- 建立统一策略接口，所有策略使用一致的输入、输出和回测协议。
- 策略参数必须版本化。
- 每次策略优化必须保存实验记录。
- 不允许使用测试集调参。
- 不允许只根据单一历史区间的收益判断策略优劣。
- 不允许将策略自动优化结果直接投入真实交易。
- 必须保留简单基准策略，避免复杂模型没有带来实际增益。
- 策略推荐必须给出适用环境、失效条件和风险提示。

## 三、三个版本之间的依赖关系

V1.1 提供市场状态、市场情报和资产趋势解释。

V1.2 使用 V1.1 的市场判断，同时结合账户资金、持仓和风险约束，形成投资决策。

V1.3 使用 V1.1 的市场环境分类和 V1.2 的组合决策约束，研究不同策略在不同市场环境下的适用性。

禁止出现以下情况：

- V1.2 自己重新实现一套与 V1.1 不一致的市场评分算法。
- V1.3 绕过 V1.0 的数据质量校验。
- 不同版本使用不同的时间对齐规则。
- 不同模块对同一个指标采用不同计算公式。
- 历史回测读取未来数据。
- 模型生成的解释被当作真实行情事实。

## 四、统一的数据和模型治理要求

所有版本必须遵循：

1. 所有行情使用 UTC 时间。
2. 所有信号必须记录计算截止时间。
3. 只能使用已经收盘的 K 线生成正式信号。
4. 保存特征版本、策略版本、模型版本和配置版本。
5. 保存原始数据来源及数据更新时间。
6. 允许使用历史数据重新计算历史信号。
7. 允许比较不同模型版本的历史表现。
8. 数据缺失或质量异常时必须阻止正式决策。
9. 指标计算和评分逻辑必须有独立测试。
10. 重要决策必须能够解释和复现。

## 五、AI 编程模型必须遵守的开发规则

### 1. 开发前

必须先阅读 V1.0 项目代码、数据库结构、接口定义和配置文件。

先输出：
- 当前项目架构分析。
- 已有功能清单。
- 需要复用的模块。
- 需要新增的模块。
- 数据库变更方案。
- 接口变更方案。
- 版本依赖关系。
- 实施计划和风险清单。

未经确认，不允许直接重构已有核心模块。

### 2. 开发过程中

必须按阶段实施，每个阶段完成后再进入下一阶段。

每个阶段必须交付：
- 代码。
- 数据库迁移脚本。
- API 文档。
- 单元测试。
- 集成测试。
- 测试结果。
- 变更说明。
- 未完成事项。

禁止一次性生成整个版本的全部代码。

禁止为了通过测试而删除测试用例或弱化断言。

禁止只生成接口和空实现后宣称功能完成。

### 3. 验证要求

每个功能都必须有明确的验收标准。

至少包含：
- 正常场景。
- 边界场景。
- 异常场景。
- 重复执行场景。
- 数据缺失场景。
- 历史数据重算场景。
- 时间对齐和未来数据泄漏测试。
- 版本兼容测试。

涉及交易决策和策略回测的功能，必须验证手续费、滑点、现金约束和仓位约束。

### 4. 交付要求

每个版本完成时必须输出：

1. 已完成的功能。
2. 未完成的功能。
3. 数据库变更。
4. API 变更。
5. 新增配置项。
6. 自动化测试结果。
7. 回测结果（适用时）。
8. 已知问题。
9. 部署和升级步骤。
10. 下一版本的依赖事项。

## 六、统一产品边界

CTI 首要目标是研究质量和风险控制，而不是追求高频交易或短期收益。

V1.1–V1.3 均沿用 V1.0 的边界：

- 现货研究。
- 不使用杠杆。
- 不做空。
- 不自动执行真实交易。
- 不承诺收益。
- 不把 AI 生成的推测当作事实。
- 不因某个币短期涨幅较高就自动提高投资评级。

任何新增模型或指标，都必须通过历史验证和对照实验后才能进入正式评分或决策链路。

**最终目标：构建一套有数据依据、有明确风险约束、有历史验证能力、可解释、可复现、能够持续评估策略有效性的加密资产投资研究系统。**
