# 0. AI Coding Agent 执行总则

本文件是项目工程实施规范，不是产品介绍文档。

AI Coding Agent 必须按照本文件规定的工程结构、业务规则、算法公式、接口契约和测试要求进行开发。

## 0.1 开发原则

1. 在现有 V1.0 项目基础上增量开发。
2. 不允许未经分析就重构现有模块。
3. 不允许删除 V1.0 已有功能。
4. 不允许擅自修改已有数据库字段含义。
5. 不允许使用未经确认的数据源或虚构接口。
6. 不允许只实现接口和页面而不实现真实业务逻辑。
7. 不允许只写 Happy Path 测试。
8. 所有关键算法必须有独立单元测试。
9. 所有数据处理必须考虑重复、缺失、延迟、异常值。
10. 所有交易策略必须避免未来函数。
11. 所有资金计算必须考虑手续费、滑点和现金约束。
12. 不允许将回测收益作为未来收益承诺。
13. 第一阶段不接入真实交易下单接口。

# 1. 产品总体设计

## 1.1 产品定位

CTI 是一个面向 BTC、ETH 和主流山寨币的量化趋势分析、投资组合管理和策略研究系统。

产品不是价格预测器，而是基于市场数据建立可解释、可验证的投资决策辅助系统。

核心流程：

行情采集
→ 数据质量校验
→ 技术指标计算
→ 市场状态识别
→ 多维趋势分析
→ 交易信号生成
→ 投资组合管理
→ 模拟交易
→ 绩效分析
→ 策略研究
→ 模型迭代。

# 3.1 模块一：市场全景数据

## 3.1.1 功能要求

建立统一市场快照。

每个计算时间点至少生成：

- BTC 趋势。
- ETH 趋势。
- ETH/BTC 相对强度。
- 市场广度。
- 市场成交额变化。
- BTC Dominance（数据源可用时）。
- TOTAL（数据源可用时）。
- TOTAL3（数据源可用时）。
- 市场风险状态。

必须区分：

- 原始行情。
- 外部市场指标。
- 计算指标。
- 模型结论。

## 3.1.2 数据源设计

Binance 数据：

- BTCUSDT。
- ETHUSDT。
- ETHBTC。
- 首批 7 个币种交易对。

外部数据：

- BTC Dominance。
- TOTAL。
- TOTAL3。

外部数据适配必须采用 Provider 模式。

接口：

```java
public interface MarketOverviewProvider {

    String getProviderCode();

    MarketOverviewSnapshot fetchSnapshot();

    List<MarketOverviewSnapshot> fetchHistory(
        Instant startTime,
        Instant endTime
    );
}
```

具体 Provider 不得直接耦合业务评分逻辑。

外部数据源必须配置：

- provider_code
- base_url
- api_key_ref
- timeout
- retry_policy
- enabled
- data_delay_tolerance

API Key 只允许通过环境变量或密钥管理服务注入。

不得写入 Git。

## 3.1.3 市场广度计算

输入：首批 7 个交易对的已闭合日 K 线。

定义：

```text
breadth_above_ema50 =
    count(close > EMA50) / valid_symbol_count

advancers_ratio =
    count(return_1d > 0) / valid_symbol_count

strong_symbols_ratio =
    count(trend_score >= 75) / valid_symbol_count
```

要求：

- 分母只使用数据有效且已闭合的币种。
- 有效币种少于 5 个时，市场广度状态标记为 LOW_CONFIDENCE。
- 不允许把缺失币种按下跌处理。
- 记录 valid_symbol_count。

## 3.1.4 验收测试

测试场景：

1. 7 个币种全部高于 EMA50，广度应为 1。
2. 7 个币种全部低于 EMA50，广度应为 0。
3. 4 个有效币种，其余缺失，应输出 LOW_CONFIDENCE。
4. 某币种 K 线未闭合，不得参与正式计算。
5. 相同时间重复执行，结果必须一致。

# 3.2 模块二：衍生品数据

## 3.2.1 功能范围

首批采集：

- Open Interest。
- Funding Rate。
- Taker Buy/Sell Volume。
- Premium Index。

后续可增加：

- Long/Short Ratio。
- Liquidation。
- Top Trader Ratio。

数据源优先使用 Binance USDⓈ-M Futures 官方市场数据接口。

注意：衍生品数据用于现货市场风险辅助判断，不代表现货资金实际流入流出。

## 3.2.2 Provider 接口

```java
public interface DerivativesDataProvider {

    String getProviderCode();

    OpenInterestSnapshot fetchOpenInterest(

    );

    FundingRateSnapshot fetchFundingRate(
        String symbol
    );

    TakerVolumeSnapshot fetchTakerVolume(
        String symbol,
        Instant startTime,
        Instant endTime
    );

    PremiumIndexSnapshot fetchPremiumIndex(
        String symbol
    );

```

不同接口的时间粒度可能不同。

必须保存：

- event_time
- collect_time
- provider_code
- symbol
- interval
- raw_payload
- normalized_value

## 3.2.3 指标计算

OI 变化率：

```text
oi_change_4h =
    OI_t / OI_t-4h - 1
```

Funding Rate 标准化：

```text
funding_z20 =
    (funding_t - mean(funding, 20))
    / std(funding, 20)
```

主动买入比例：

```text
taker_buy_ratio =
    taker_buy_volume
    / (taker_buy_volume + taker_sell_volume)
```

价格与 OI 组合：

| 价格变化 | OI 变化 | 解释 |
|---|---|---|
| 上涨 | 上升 | 杠杆参与增加 |
| 上涨 | 下降 | 可能存在空头回补 |
| 下跌 | 上升 | 杠杆参与增加，可能存在新增空头 |
| 下跌 | 下降 | 可能存在多头平仓或去杠杆 |

这些只是观察标签，不是确定的交易方向。

## 3.2.4 异常数据处理

以下情况必须标记异常：

- OI 为负数。
- Funding Rate 缺失。
- 时间戳倒退。
- 同一时间重复数据。
- 价格或数量为 NaN。
- 数据延迟超过配置阈值。

不得对缺失的 Funding Rate 自动填充为 0。

## 3.2.5 验收测试

必须覆盖：

- 正常数据。
- 零值。
- 负值。
- 缺失值。
- 重复数据。
- 延迟数据。
- 数据时间不一致。
- API 限频。
- API 超时。
- 服务恢复后补采。

# 3.3 模块三：新闻事件中心

## 3.3.1 功能要求

新闻模块分为：

1. 新闻采集。
2. 新闻去重。
3. 新闻分类。
4. 新闻与币种关联。
5. 事件影响评级。
6. 新闻检索。
7. 趋势解释引用。

新闻采集必须使用明确授权的 API、RSS 或官方公告渠道。

禁止绕过网站访问限制。

## 3.3.2 新闻数据模型

```java
public class NewsEvent {

    private String eventId;

    private String providerCode;

    private String title;

    private String sourceUrl;

    private String sourceName;

    private Instant publishedAt;

    private Instant eventAt;

    private String category;

    private String sentiment;

    private String impactLevel;

    private BigDecimal confidence;

    private String summary;

    private String contentHash;
}
```

事件类别：

```text
MACRO
REGULATION
ETF
EXCHANGE
PROJECT
STABLECOIN
SECURITY
TOKEN_UNLOCK
OTHER
```

情绪：

```text
POSITIVE
NEGATIVE
NEUTRAL
UNCERTAIN
```

影响等级：

```text
LOW
MEDIUM
HIGH
CRITICAL
```

## 3.3.3 新闻去重

第一层：URL 去重。

第二层：标题规范化后计算 Hash。

第三层：相似标题识别。

同一事件由多个媒体转载时：

- 保留原始来源。
- 建立关联新闻。
- 不重复累计情绪分。
- 优先选择官方公告作为事件主记录。

## 3.3.4 AI 新闻分类接口

定义：

```python
class NewsClassification(BaseModel):
    category: str
    sentiment: str
    impact_level: str
    confidence: float
    related_assets: list[str]
    summary: str
    evidence: list[str]
```

要求：

- AI 输出必须经过 Pydantic 校验。
- 置信度必须在 0～1。
- 不允许 AI 生成不存在的原文事实。
- 新闻正文缺失时只能基于标题分类，并降低置信度。
- 无法确定影响方向时使用 UNCERTAIN。
- 必须保留原文 URL。

## 3.3.5 新闻事件评分

初始事件影响分：

```text
event_impact =
    severity_score
    * source_reliability
    * time_decay
    * relevance_score
```

其中：

- severity_score：事件影响等级映射。
- source_reliability：来源可信度。
- time_decay：时间衰减。
- relevance_score：与目标币种相关程度。

时间衰减：

```text
time_decay =
    exp(-ln(2) * age_hours / half_life_hours)
```

不同事件类型使用不同 half_life_hours。

该评分只用于事件排序和风险提醒。

V1.1 不允许将新闻评分直接作为买卖决策的主要依据。

## 3.3.6 验收

- 相同 URL 不得重复入库。
- 相同新闻标题 Hash 不得重复计分。
- 官方公告必须能追溯原始 URL。
- AI JSON 不合法时不得写入正式事件。
- AI 服务超时不影响行情采集和趋势计算。
- 新闻没有关联币种时允许标记 MARKET_WIDE。

只接入 BTC、ETH。

- Exchange Inflow。
- Exchange Outflow。
- Exchange Netflow。

## 3.4.2 指标定义

```text
exchange_netflow =
    exchange_inflow - exchange_outflow
```

要求：

- 统一资产单位。
- 统一时间粒度。

- 数据源变更必须记录 provider_code。

## 3.5.1 设计原则

保留 V1.0 原始趋势评分。

新增独立维度：

- Sentiment Score。
- Data Confidence。

不允许将风险、趋势、情绪简单混为一个没有解释能力的分数。

## 3.5.2 评分权重

趋势与市场结构总分 85：

| 维度 | 权重 |
|---|---:|
| 趋势结构 | 25 |
| 动量 | 15 |
| 相对强度 | 15 |
| 成交量 | 15 |
| 市场环境 | 15 |

辅助情报总分 15：

| 维度 | 权重 |
|---|---:|
| 衍生品风险调整 | 10 |
| 链上及事件辅助 | 5 |

实际实现时必须将 Trend、Risk、Sentiment 独立输出。

上表用于定义综合趋势判断候选特征，不代表 Risk Score 和 Sentiment Score 可以直接加到 Trend Score 中。

正式实现采用：

```text
trend_score = weighted_sum(
    trend_structure,
    momentum,
    relative_strength,
    volume,
    market_environment
)
```

```text
risk_score = weighted_sum(
    volatility_risk,
    derivatives_risk,
    market_regime_risk,
    data_quality_risk
)
```

```text
sentiment_score = weighted_sum(
    funding_sentiment,
    news_sentiment,
    onchain_context
)
```

每个分项均映射到 0～100。

缺失特征不按 0 分处理。

有效指标重新归一化，同时降低 Data Confidence。

## 3.5.3 置信度

定义：

```text
data_confidence =
    valid_feature_weight / total_feature_weight
```

核心行情数据不完整时：

```text
data_confidence < 0.8
```

正式交易信号输出 NO_TRADE。

辅助数据缺失可以继续输出基础趋势判断，但必须标注数据不完整。

## 3.5.4 信号生成

信号候选：

```text

BUY
HOLD
REDUCE
EXIT
NO_TRADE
```

基础规则：

BUY：

- Trend Score >= 75。
- BTC 市场状态不是 STRONG_BEAR。
- Data Confidence >= 0.8。
- 4h 趋势确认。
- 风险等级不为 CRITICAL。

HOLD：

- Trend Score 60～74。

REDUCE：

- Trend Score 30～44。
- 只对已有持仓产生减仓建议。

EXIT：

- Trend Score < 30。
- 或触发策略退出规则。

NO_TRADE：

- 核心数据缺失。
- 价格异常。
- 市场风险严重。
- 计算窗口不足。

以上阈值是初始模型参数，必须配置化并通过回测验证。

## 3.5.5 验收

必须使用固定测试数据验证：

- 趋势分数边界。
- 权重归一化。
- 指标缺失。
- 数据置信度。
- 市场风险过滤。
- 4h 未闭合。
- 同一输入重复计算。
- 模型版本变化。

相同输入、相同模型版本、相同参数必须得到相同结果。

# 5. V1.3 智能策略研究详细实施规范

# 5.1 策略注册中心

统一策略接口：

```python
from abc import ABC, abstractmethod

class BaseStrategy(ABC):

    @abstractmethod
    def strategy_code(self) -> str:
        pass

    @abstractmethod
    def strategy_version(self) -> str:
        pass

    @abstractmethod
    def get_parameters(self) -> dict:
        pass

    @abstractmethod
    def calculate_features(self, data):
        pass

    @abstractmethod
    def generate_signal(self, data):
        pass

    @abstractmethod
    def calculate_exit(self, data, position):
        pass
```

所有策略必须遵循统一输入输出。

输出至少包含：

```json
{
  "strategyCode": "EMA_TREND",
  "strategyVersion": "1.0.0",
  "symbol": "BTCUSDT",
  "signal": "BUY",
  "score": 80,
  "targetWeight": 0.15,
  "stopPrice": 60000,
  "signalTime": "2026-11-06T00:00:00Z",
  "explanation": []
}
```

以上仅为结构示例，具体价格和评分由运行时计算。

## 5.1.1 首批策略

### EMA Trend

规则：

```text
EMA20 > EMA50 > EMA200
AND close > EMA20
```

满足条件后，根据动量和 ADX 决定趋势强度。

### Donchian Breakout

```text
close_t > max(high[t-N:t])
```

当前 K 线不能进入历史最高价窗口。

默认研究参数：

- N = 20。
- N = 55。

### Momentum

```text
momentum_n = close_t / close_t-n - 1
```

计算 7d、14d、30d 动量。

### Relative Strength Rotation

```text
relative_strength =
    asset_return_n - BTC_return_n
```

按照相对强度排序，结合趋势过滤。

### Mean Reversion

使用标准化偏离：

```text
z_score =
    (close - rolling_mean) / rolling_std
```

仅在 SIDEWAYS 市场状态下研究。

不得在强趋势市场直接使用均值回归策略。

# 5.2 市场状态识别

## 5.2.1 规则模型

初始状态：

```text

TRENDING_BEAR
SIDEWAYS

```

- BTC EMA20。
- BTC EMA50。
- BTC EMA200。
- ADX14。
- ATR%。
- 20 日实现波动率。
- 市场广度。

示例：

TRENDING_BULL：

```text
close > EMA200
AND EMA50 > EMA200
AND ADX14 >= configured_threshold
```

TRENDING_BEAR：

```text
close < EMA200
AND EMA50 < EMA200

```

SIDEWAYS：

- 趋势结构不明确。

优先级：

```text
direction_regime:
BULL / BEAR / SIDEWAYS

volatility_regime:
LOW / NORMAL / HIGH
```

这样避免一个市场同时满足多个互相矛盾的单一状态。

规则模型稳定后，允许增加：

- Hidden Markov Model。

- 输入特征版本。

- 训练时间区间。
- 训练数据范围。
- 状态概率。
- 状态映射规则。

不允许直接把聚类标签解释为牛市或熊市。

# 5.3 策略融合

多个策略同时产生信号时，统一融合。

初始公式：

```text
ensemble_score =
    sum(strategy_score_i * strategy_weight_i)
    / sum(valid_strategy_weight_i)
```

策略权重必须满足：

```text
0 <= weight_i <= 1
sum(weight_i) = 1
```

如果策略数据缺失：

- 排除无效策略。
- 对剩余策略权重重新归一化。
- 降低融合置信度。

融合结果还必须经过：

- BTC 市场状态过滤。
- 波动率过滤。
- 组合风险限制。
- 现金限制。
- 数据置信度检查。

不能仅因为 3 个策略看多、1 个策略看空，就直接产生 BUY。

策略之间的相关性也需要评估，避免多个高度相似策略重复投票。

# 5.4 参数优化

初始支持：

- Grid Search。
- Random Search。

后续支持 Bayesian Optimization。

优化参数：

- EMA 周期。
- Donchian 周期。
- ATR 止损倍数。
- ADX 阈值。
- 动量窗口。
- 趋势评分权重。

目标函数：

不允许只优化总收益。

建议采用约束优化：

```text
maximize:
    risk_adjusted_return

subject to:
    max_drawdown <= configured_limit
    trade_count >= minimum_trades
    fee_ratio <= configured_fee_ratio
```

需要保留完整参数搜索记录。

防止参数过拟合：

1. 时间顺序划分训练集、验证集和测试集。
2. 测试集只允许最终评估。
3. 参数只能在训练集和验证集选择。
4. 采用 Walk-forward。
5. 记录所有实验，不得只保留最优结果。

Walk-forward 默认：

- Train：24 个月。
- Validation：6 个月。
- Test：6 个月。
- 滚动前进：3 个月。

历史数据不足时允许缩短窗口，但必须降低实验等级并明确标注。

# 9. 回测和模拟交易验证规范

这是整个项目最重要的工程约束之一。

## 9.1 禁止未来函数

信号在 K 线 t 收盘后生成。

最早执行时间：

```text
t + 1 open
```

禁止：

- 使用尚未闭合的 K 线。
- 使用未来价格计算当前指标。
- 使用未来新闻发布时间。
- 使用未来链上数据。
- 使用未来交易量。
- 使用全样本均值标准差进行历史归一化。
- 使用测试集参数反向优化训练集。

## 9.2 费用模型

至少包含：

- Maker Fee。
- Taker Fee。
- Slippage。
- 最小交易金额。
- 交易数量精度。
- 价格精度。

费用模型必须可配置。

## 9.3 数据切分

必须按照时间顺序：

```text
Train
→ Validation
→ Test
```

禁止随机打乱时间序列。

默认 Walk-forward：

- Train 24 个月。
- Validation 6 个月。
- Test 6 个月。
- 每 3 个月滚动一次。

## 9.4 基准策略

必须对比：

- BTC Buy & Hold。
- ETH Buy & Hold。
- 等权组合。
- EMA20/EMA50。
- Donchian 20。
- V1.0 策略。

## 9.5 回测报告

必须包含：

- 总收益。
- CAGR。
- Sharpe。
- Sortino。
- 最大回撤。
- Calmar。
- 胜率。
- Profit Factor。
- 交易次数。
- 平均持仓时间。
- 换手率。
- 手续费。
- 滑点。
- 资金利用率。
- 样本外表现。

## 9.6 回测一致性测试

对于固定行情数据和固定策略配置：

- Java 计算的信号与 Python 计算结果必须一致。
- 同样的输入重复回测结果必须一致。
- 同一信号不能重复产生交易。
- 资金余额必须与成交流水对得上。
- 净值必须能从持仓、现金和价格重新计算出来。

# 15. 最终验收标准

整个项目不能以代码编译成功作为交付标准。

必须满足：

## 工程质量

- Java 编译成功。
- Python 测试通过。
- 数据库迁移成功。
- API 契约完整。
- 无严重安全问题。
- 日志和监控完整。

## 数据质量

- 数据来源明确。
- 数据时间明确。
- 数据缺失有标记。
- 数据重复有治理。
- 历史数据可复现。

## 算法质量

- 指标公式明确。
- 指标有独立测试。
- 评分有解释。
- 信号有版本。
- 参数可追溯。

## 投资决策质量

- 仓位符合限制。
- 风险预算生效。
- 手续费和滑点计入。
- 模拟交易可以复现。
- 账户流水能够对账。

## 策略研究质量

- 时间顺序切分。
- 不存在未来函数。
- 有基准策略。
- 有 Walk-forward。
- 有样本外测试。
- 有模型健康度监控。

## 产品质量

- 市场状态可查看。
- 趋势判断可解释。
- 投资组合可管理。
- 模拟交易可运行。
- 策略可以比较。
- AI 研究结果可追溯。

最终交付目标：

将 CTI 从一个基础趋势评分工具，升级为一个完整的量化研究和投资决策辅助平台。

**核心原则：所有结论必须有数据依据，所有算法必须有测试，所有策略必须有回测，所有资金操作必须有流水，所有 AI 输出必须可以追溯。**
