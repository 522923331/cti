# 0. AI Coding Agent 执行总则

本文件是项目工程实施规范，不是产品介绍文档。

AI Coding Agent 必须按照本文件规定的工程结构、业务规则、算法公式、接口契约和测试要求进行开发。

## 0.1 开发原则

1. 在现有 V1.0 项目基础上增量开发。
2. 不允许未经分析就重构现有模块。
3. 不允许删除 V1.0 已有功能。
4. 不允许擅自修改已有数据库字段含义。
5. 不允许使用未经确认的数据源或虚构接口。
6. 不允许只实现接口和页面而不实现真实业务逻辑。
7. 不允许只写 Happy Path 测试。
8. 所有关键算法必须有独立单元测试。
9. 所有数据处理必须考虑重复、缺失、延迟、异常值。
10. 所有交易策略必须避免未来函数。
11. 所有资金计算必须考虑手续费、滑点和现金约束。
12. 不允许将回测收益作为未来收益承诺。
13. 第一阶段不接入真实交易下单接口。

# 1. 产品总体设计

## 1.1 产品定位

CTI 是一个面向 BTC、ETH 和主流山寨币的量化趋势分析、投资组合管理和策略研究系统。

产品不是价格预测器，而是基于市场数据建立可解释、可验证的投资决策辅助系统。

核心流程：

行情采集
→ 数据质量校验
→ 技术指标计算
→ 市场状态识别
→ 多维趋势分析
→ 交易信号生成
→ 投资组合管理
→ 模拟交易
→ 绩效分析
→ 策略研究
→ 模型迭代。

# 3. V1.1 市场情报系统详细实施规范

# 3.1 模块一：市场全景数据

## 3.1.1 功能要求

建立统一市场快照。

每个计算时间点至少生成：

- BTC 趋势。
- ETH 趋势。
- ETH/BTC 相对强度。
- 市场广度。
- 市场成交额变化。
- BTC Dominance（数据源可用时）。
- TOTAL（数据源可用时）。
- TOTAL3（数据源可用时）。
- 市场风险状态。

必须区分：

- 原始行情。
- 外部市场指标。
- 计算指标。
- 模型结论。

## 3.1.2 数据源设计

Binance 数据：

- BTCUSDT。
- ETHUSDT。
- ETHBTC。
- 首批 7 个币种交易对。

外部数据：

- BTC Dominance。
- TOTAL。
- TOTAL3。

外部数据适配必须采用 Provider 模式。

接口：

```java
public interface MarketOverviewProvider {

    String getProviderCode();

    MarketOverviewSnapshot fetchSnapshot();

    List<MarketOverviewSnapshot> fetchHistory(
        Instant startTime,
        Instant endTime
    );
}
```

具体 Provider 不得直接耦合业务评分逻辑。

外部数据源必须配置：

- provider_code
- base_url
- api_key_ref
- timeout
- retry_policy
- enabled
- data_delay_tolerance

API Key 只允许通过环境变量或密钥管理服务注入。

不得写入 Git。

## 3.1.3 市场广度计算

输入：首批 7 个交易对的已闭合日 K 线。

定义：

```text
breadth_above_ema50 =
    count(close > EMA50) / valid_symbol_count

advancers_ratio =
    count(return_1d > 0) / valid_symbol_count

strong_symbols_ratio =
    count(trend_score >= 75) / valid_symbol_count
```

要求：

- 分母只使用数据有效且已闭合的币种。
- 有效币种少于 5 个时，市场广度状态标记为 LOW_CONFIDENCE。
- 不允许把缺失币种按下跌处理。
- 记录 valid_symbol_count。

## 3.1.4 验收测试

测试场景：

1. 7 个币种全部高于 EMA50，广度应为 1。
2. 7 个币种全部低于 EMA50，广度应为 0。
3. 4 个有效币种，其余缺失，应输出 LOW_CONFIDENCE。
4. 某币种 K 线未闭合，不得参与正式计算。
5. 相同时间重复执行，结果必须一致。

# 3.2 模块二：衍生品数据

## 3.2.1 功能范围

首批采集：

- Open Interest。
- Funding Rate。
- Taker Buy/Sell Volume。
- Premium Index。

后续可增加：

- Long/Short Ratio。
- Liquidation。
- Top Trader Ratio。

数据源优先使用 Binance USDⓈ-M Futures 官方市场数据接口。

注意：衍生品数据用于现货市场风险辅助判断，不代表现货资金实际流入流出。

## 3.2.2 Provider 接口

```java
public interface DerivativesDataProvider {

    String getProviderCode();

    OpenInterestSnapshot fetchOpenInterest(
        String symbol
    );

    FundingRateSnapshot fetchFundingRate(
        String symbol
    );

    TakerVolumeSnapshot fetchTakerVolume(
        String symbol,
        Instant startTime,
        Instant endTime
    );

    PremiumIndexSnapshot fetchPremiumIndex(
        String symbol
    );

```

不同接口的时间粒度可能不同。

必须保存：

- event_time
- collect_time
- provider_code
- symbol
- interval
- raw_payload
- normalized_value

## 3.2.3 指标计算

OI 变化率：

```text
oi_change_4h =
    OI_t / OI_t-4h - 1
```

Funding Rate 标准化：

```text
funding_z20 =
    (funding_t - mean(funding, 20))
    / std(funding, 20)
```

主动买入比例：

```text
taker_buy_ratio =
    taker_buy_volume
    / (taker_buy_volume + taker_sell_volume)
```

价格与 OI 组合：

| 价格变化 | OI 变化 | 解释 |
|---|---|---|
| 上涨 | 上升 | 杠杆参与增加 |
| 上涨 | 下降 | 可能存在空头回补 |
| 下跌 | 上升 | 杠杆参与增加，可能存在新增空头 |
| 下跌 | 下降 | 可能存在多头平仓或去杠杆 |

这些只是观察标签，不是确定的交易方向。

## 3.2.4 异常数据处理

以下情况必须标记异常：

- OI 为负数。
- Funding Rate 缺失。
- 时间戳倒退。
- 同一时间重复数据。
- 价格或数量为 NaN。
- 数据延迟超过配置阈值。

不得对缺失的 Funding Rate 自动填充为 0。

## 3.2.5 验收测试

必须覆盖：

- 正常数据。
- 零值。
- 负值。
- 缺失值。
- 重复数据。
- 延迟数据。
- 数据时间不一致。
- API 限频。
- API 超时。
- 服务恢复后补采。

# 3.3 模块三：新闻事件中心

## 3.3.1 功能要求

新闻模块分为：

1. 新闻采集。
2. 新闻去重。
3. 新闻分类。
4. 新闻与币种关联。
5. 事件影响评级。
6. 新闻检索。
7. 趋势解释引用。

新闻采集必须使用明确授权的 API、RSS 或官方公告渠道。

禁止绕过网站访问限制。

## 3.3.2 新闻数据模型

```java
public class NewsEvent {

    private String eventId;

    private String providerCode;

    private String title;

    private String sourceUrl;

    private String sourceName;

    private Instant publishedAt;

    private Instant eventAt;

    private String category;

    private String sentiment;

    private String impactLevel;

    private BigDecimal confidence;

    private String summary;

    private String contentHash;
}
```

事件类别：

```text
MACRO
REGULATION
ETF
EXCHANGE
PROJECT
STABLECOIN
SECURITY
TOKEN_UNLOCK
OTHER
```

情绪：

```text
POSITIVE
NEGATIVE
NEUTRAL
UNCERTAIN
```

影响等级：

```text
LOW
MEDIUM
HIGH
CRITICAL
```

## 3.3.3 新闻去重

第一层：URL 去重。

第二层：标题规范化后计算 Hash。

第三层：相似标题识别。

同一事件由多个媒体转载时：

- 保留原始来源。
- 建立关联新闻。
- 不重复累计情绪分。
- 优先选择官方公告作为事件主记录。

## 3.3.4 AI 新闻分类接口

定义：

```python
class NewsClassification(BaseModel):
    category: str
    sentiment: str
    impact_level: str
    confidence: float
    related_assets: list[str]
    summary: str
    evidence: list[str]
```

要求：

- AI 输出必须经过 Pydantic 校验。
- 置信度必须在 0～1。
- 不允许 AI 生成不存在的原文事实。
- 新闻正文缺失时只能基于标题分类，并降低置信度。
- 无法确定影响方向时使用 UNCERTAIN。
- 必须保留原文 URL。

## 3.3.5 新闻事件评分

初始事件影响分：

```text
event_impact =
    severity_score
    * source_reliability
    * time_decay
    * relevance_score
```

其中：

- severity_score：事件影响等级映射。
- source_reliability：来源可信度。
- time_decay：时间衰减。
- relevance_score：与目标币种相关程度。

时间衰减：

```text
time_decay =
    exp(-ln(2) * age_hours / half_life_hours)
```

不同事件类型使用不同 half_life_hours。

该评分只用于事件排序和风险提醒。

V1.1 不允许将新闻评分直接作为买卖决策的主要依据。

## 3.3.6 验收

- 相同 URL 不得重复入库。
- 相同新闻标题 Hash 不得重复计分。
- 官方公告必须能追溯原始 URL。
- AI JSON 不合法时不得写入正式事件。
- AI 服务超时不影响行情采集和趋势计算。
- 新闻没有关联币种时允许标记 MARKET_WIDE。

## 3.4.1 首批范围

只接入 BTC、ETH。

先实现 Provider 接口，具体供应商可配置。

public interface OnchainDataProvider {

首批指标：

- Exchange Inflow。
- Exchange Outflow。
- Exchange Netflow。
- Active Addresses。
- Transaction Count。

## 3.4.2 指标定义

```text
exchange_netflow =
    exchange_inflow - exchange_outflow
```

要求：

- 统一资产单位。
- 统一时间粒度。
- 保留数据供应商原始单位。
- 保存数据采集时间。

- 不同数据源不能未经单位转换直接相加。
- 数据缺失不允许填 0。
- 数据源变更必须记录 provider_code。
- 历史数据重新采集不得覆盖已验证的原始数据而不留版本记录。

# 3.5 模块五：V1.1 多维趋势评分

## 3.5.1 设计原则

保留 V1.0 原始趋势评分。

新增独立维度：

- Trend Score。
- Risk Score。
